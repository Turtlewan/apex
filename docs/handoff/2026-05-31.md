### Cluster 1–4 gaps exposed by the pilot?

Minor observations, not blockers:
1. **Permission friction.** `npm run build` was repeatedly blocked by the auto mode classifier across this session. This isn't a cluster-4 gap (apex-code's recipe loop is correct) but a harness UX issue on Windows — the DeepSeek backend's permission model flags `next build` as "not evaluated." This would slow a real build loop. Mitigation: pre-approving the recipe's commands via settings.json in production projects.
2. **stack_skills reading was manual.** In this pilot, the `stack_skills` binding in `status.md` was read directly by the human + Claude, not by an automated `apex-code` session-start hook. The binding itself (field on `status.md`, format in the orchestrate template) is correct, but the *programmatic read* is assumed by ADR-005/006 — the pilot didn't exercise the automated session-start extraction because this session was a one-off, not an `apex-code` session. This is a validation gap that planning should note as a live-test to-do.
3. **Recovery loop demo was seeded, not natural.** The spec asked for a "naturally surfaces" error, but the initial code was correct. The demo required a deliberate error injection. In a real build with a less experienced developer or an ambiguous spec, natural errors are likely — but the pilot didn't empirically trigger one during the feature build because the patterns were followed correctly. This is evidence that `apex-nextjs` patterns are clear enough to prevent common mistakes on the first pass.
