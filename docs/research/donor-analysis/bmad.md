# BMAD-METHOD — absorption analysis for APEX

Donor: **BMAD-METHOD** ("Breakthrough Method for Agile AI-Driven Development"), v6.x, MIT, ~46.7k★, `bmad-code-org/BMAD-METHOD`. Pure-prompt/markdown+YAML agent framework (JS tooling only for the installer). Researched from the repo, docs.bmad-method.org, DeepWiki, and third-party writeups (June 2026).

---

## What it is (sourced)

BMAD turns "chaotic AI interactions into systematic, spec-driven development" by simulating an **agile software team as a pipeline of named agent personas**, each operating in its own (ideally fresh) context window and emitting a **versioned document artifact** that becomes the input for the next agent. The flagship idea: "The PRD tells the architect what constraints matter. The architecture tells the dev agent which patterns to follow. Story files give focused, complete context for implementation." (workflow-map docs).

**Four phases** (docs.bmad-method.org/reference/workflow-map):
- **Phase 1 — Analysis (optional):** brainstorming, domain/market/technical research, product brief, PR-FAQ. Agents: `bmad-brainstorming`, `bmad-*-research`, `bmad-product-brief`, `bmad-prfaq`.
- **Phase 2 — Planning:** "what to build and for whom." `bmad-prd` (create/update/validate) → `prd.md`, plus `bmad-ux` → **`DESIGN.md`** and **`EXPERIENCE.md`**, `decision-log.md`, `addendum.md`.
- **Phase 3 — Solutioning:** "how to build it." `bmad-create-architecture` → `architecture.md` (with ADRs); `bmad-create-epics-and-stories`; `bmad-check-implementation-readiness`.
- **Phase 4 — Implementation:** story-by-story execution. `bmad-sprint-planning`, `bmad-create-story`, `bmad-dev-story`, `bmad-code-review`, `bmad-correct-course`, `bmad-sprint-status`, `bmad-retrospective`, `bmad-investigate` → `sprint-status.yaml`, `story-[slug].md`, working code.

**Named personas** (12+ in v5, "19+ specialized agents" in v6): Analyst (Mary), PM (John), Architect (Winston), UX Designer, Scrum Master, Developer, QA, Tech Writer, brainstorming facilitator (Carson). "Party Mode" lets multiple personas collaborate in one session.

**Scale-Adaptive Routing** — matches process depth to project size (mintlify/deepwiki):
- L0 single atomic change (1 story) · L1 small feature (1–10) · L2 medium (5–15) · L3 complex integration (12–40) · L4 enterprise (40+).
- Three **tracks**: **Quick Flow** (L0–1, tech-spec only, no PRD, 1–2 stories) · **BMad Method** (L2–3, full pipeline) · **Enterprise** (L4, adds Security Architecture, DevOps Strategy, Test Strategy).

## Mechanism inventory

1. **Persona pipeline w/ versioned artifact handoff** — each role produces a named doc consumed by the next; artifacts double as audit/compliance evidence (SOC2/HIPAA).
2. **Story file** — `story-[slug].md`: a single self-contained unit holding "focused, complete context for implementation" so the dev agent needs nothing else loaded. Carries status fields; SM marks DONE and unlocks dependents.
3. **Document sharding** — large artifacts (PRD) split into a directory (`prd/index.md` + per-epic files). Three **load strategies**: `FULL_LOAD`, `INDEX_GUIDED` (load index, AI selects), `SELECTIVE_LOAD` (named files via template vars). Claimed 82% context cut (45k→8k for one-epic story creation).
4. **Step-file architecture (v6)** — monolithic workflows fragmented into per-step files; loads ~2–3k tokens/step instead of 15k upfront. Frontmatter tracking (`lastStep`, `stepsCompleted`) enforces sequential loading and lets long tasks pause/resume mid-workflow. Claimed ~80% reduction/workflow.
5. **Fresh-context principle** — start a new conversation per major phase; don't accumulate PRD+arch+impl context.
6. **`project-context.md` constitution** — captures project's technical preferences/conventions as "implementation constraints that prevent agents defaulting to generic best practices." Generated by `bmad-generate-project-context`.
7. **Brownfield `document-project` workflow** — scans an existing codebase and emits `docs/index.md` (master discovery file), `project-overview.md`, `architecture.md`, `source-tree-analysis.md`, conditional `api-contracts.md` / `data-models.md`. Dual-discovery (checks both `PRD.md` and `prd/index.md`).
8. **`index.md` as discovery mechanism** — workflows read it (via `input_file_patterns`) to decide what to load.
9. **Scale-adaptive routing** — L0–L4 → track selection; small work skips PRD entirely.
10. **UX-Designer artifact** — dedicated `DESIGN.md` + `EXPERIENCE.md` produced before dev.
11. **Web bundles** — run agents inside ChatGPT/Gemini/Claude Projects to offload cost.
12. **Retrospective / correct-course** — explicit per-sprint learning + mid-course adjustment workflows.

## Top absorbable candidates

### 1. UX/App-Flow artifact (DESIGN.md + EXPERIENCE.md analogue) — fills APEX's known gap
- **Change in APEX:** add an optional planning-mode artifact `docs/architecture/app-flow.md` (or `ui-spec.md`) produced by apex-ui-ux-design during planning for UI-bearing projects — screen inventory, per-screen states, navigation/flow, key interactions. Seed a stub in apex-init; reference it from apex-plan's readiness gate when the build has a UI.
- **Token-cost: Low.** A per-project doc written once in planning and loaded only by UI specs/reviews — not always-on context.
- **Lean:** one new optional doc + two one-line references (apex-init stub, apex-plan gate). Don't add new agents.

### 2. Scale-adaptive track (skip-the-PRD lane for trivial work)
- **Change in APEX:** add an explicit "complexity lane" to apex-plan: L0/L1 work (single atomic change / ≤ a few files) skips PRD/ADR ceremony and goes straight to a one-task spec; reserve full planning artifacts for larger builds. APEX already has the inverse "split if >3 files" — add the "collapse if trivial" side.
- **Token-cost: Low.** Pure routing rule; *reduces* tokens on small tasks.
- **Lean:** a short routing table in apex-plan (size → artifacts to produce). No new files/agents.

### 3. Project-artifact sharding + INDEX_GUIDED loading
- **Change in APEX:** when a planning doc (PRD/overview) grows large, shard into `prd/index.md` + sections and teach apex-plan/apex-code to load the index first, then only the section a spec needs (SELECTIVE_LOAD by name). Mirrors impl.md's two-tier idea but for *project* docs.
- **Token-cost: Low-to-Med.** Saves tokens at read time; the discipline itself is near-free. Med only because it adds a load-routing step authors must follow.
- **Lean:** add to apex-context-budget guidance + a one-line load rule in apex-code; apply only past a size threshold.

### 4. Brownfield codebase-mapping workflow
- **Change in APEX:** a planning workflow that scans an existing repo and emits `docs/architecture/overview.md` + a `source-tree-map.md` + conceptual `data-model.md` from real code, so APEX can onboard non-greenfield projects. (Note: `gsd-map-codebase` already in the skill list — evaluate reuse before building.)
- **Token-cost: Med.** One-time scan can be context-heavy on large repos; run once, persist artifacts, then load lazily.
- **Lean:** scope to "produce the existing doc set from code," reuse apex-init's doc templates, cap depth (index + tree + data-model, conditional api-contracts).

### 5. docs/index.md as a machine-read load manifest
- **Change in APEX:** add a tiny `docs/index.md` listing each durable doc + a one-line "load when…" so specs/reviewers select what to load instead of reading everything. Complements status.md (state) with a load-routing manifest.
- **Token-cost: Low.** Tiny always-available file that *gates* larger loads.
- **Lean:** ~20-line generated file; fold generation into apex-init.

**Explicitly NOT absorbing:** the 12-persona pipeline itself, Party Mode, web bundles, per-step file fragmentation of workflows (APEX's status.md resume + wave model already covers pause/resume at lower overhead).

## Token-cost watchlist

- **The 12–19 persona pipeline (HIGH — do not absorb):** real-world ~31,667 tokens/workflow run; $800–$2,000+/dev/month on frontier models; one build hit $3,200/week on Opus; a CRM task took 5.5h on BMAD vs 12min on OpenSpec (27×). BMAD's *own* v6 work (sharding, step-files, fresh-context) is damage control for the cost its persona ceremony creates. APEX already gets the benefit (fresh-context review) without the bill — porting the pipeline would import the exact cost APEX avoids.
- **Brownfield mapping (MED):** one-time scan inflates context on large repos; mitigate by persisting artifacts and loading lazily.
- **Sharding/INDEX_GUIDED (NET-NEGATIVE cost = good):** these are token *savers*; the only cost is author discipline.
- **Scale-adaptive lane (NET-NEGATIVE = good):** reduces tokens on small tasks.
