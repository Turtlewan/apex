## Sol plan-check sol-4 (gpt-5.6-sol xhigh, spec digest 4f43a0b)
- **BLOCK** (line 22, Assumptions / Task 5 ordering): The Stop-impact assumption says all three HOST files are written after coder tasks, but Task 5 and the Wave plan require AGENTS.md to be modified at build start. Timing matters because AGENTS.md supplies prompt and verification commands. The builder cannot satisfy both instructions.
- **BLOCK** (line 68, Task 1 and Task 4 model contract): The planner accepts and immutably records coder_model `codex`, while Task 4 must pass that value explicitly as `-Model`. The live codex-dispatch.ps1 parameter at lines 18-19 accepts only `gpt-5.6-sol` and `gpt-6-sol`; `codex` fails parameter binding before the wrapper can emit an event or ledger row.
- **BLOCK** (line 68, Task 1 wave planning): Ancestor/descendant file overlaps are split into later waves instead of refused. Because manifest entries are files, paths such as `foo` and `foo/bar.ps1` cannot both exist in any ordering: one task necessarily turns the other's ancestor into a file or directory. The advertised split deterministically reaches an operation-precondition failure. Rejecting such pairs is the simpler correct structure.
- **BLOCK** (line 68, Task 1 path safety / Security): The refusal set excludes `.gitattributes` but does not exclude a `.git` path segment. The 1.1.0 manifest contract accepts `.git/config`; in the main repo it is a regular leaf and `git status -- ... .git/config` does not expose it, while linked worktrees represent `.git` differently. Such a task can target repository-control data outside normal scope, copy, and proof guarantees. Every `.git` segment must be refused before dispatch.
- **BLOCK** (line 68, Task 1 and Task 3 task identity): No Engine limit is imposed on task-ID length, and the live validator accepts any digits plus an optional letter without a length cap. The protocol schema caps task_id at 64 characters, and codex-dispatch.ps1 lines 807-829 truncates longer IDs in events. Task 3's exact event/ledger correlation will therefore reject a valid validator-approved manifest.
- **BLOCK** (line 70, Task 3 exit/status correlation): The explicit table allows only done/done_with_concerns/failed for exits 65, 66, 73, and 77. The live wrapper's adoption path records `adopted-done`, `adopted-done_with_concerns`, or scope-suffixed variants before returning those exits (codex-dispatch.ps1 lines 2592-2646). The suffix sentence does not admit the missing adopted prefixes, so valid recovery events would be rejected.
- **BLOCK** (line 71, Task 4 integration verification): After running arbitrary AGENTS.md commands, any tree-pin movement is accepted by re-pinning and rerunning once. The baseline runner can modify files, stage files, or even move HEAD; tree-pin observes these changes but does not authorize them. A stable second run can therefore normalize an off-manifest index/HEAD mutation and let Commit-EngineWave commit it. No integration scope/index allowlist or restoration mechanism closes this hole.
- **BLOCK** (line 71, Task 4 MaxParallel behavior): The CLI `-MaxParallel` is treated as the planner's effective capacity, but that value is never supplied to the wrapper. The live wrapper independently uses the spec frontmatter ceiling and MachineCeiling 4. For example, frontmatter ceiling 1 plus `-MaxParallel 2` permits an ultra task in the planner, but the wrapper will refuse that weight on every attempt with exit 79 until the Engine parks. Override versus cap semantics need one authoritative mechanism.
- **BLOCK** (line 146, Scope acceptance criterion): A before/after `git status --porcelain -uall --ignored` inventory cannot prove that only authorized files changed in a dirty tree. Further edits to an already-M, D, untracked, or ignored path leave the same porcelain entry. The live build repo already contains many such paths, so this criterion can pass despite out-of-scope content changes; hashes or saved file identities are required.
- **FLAG** (line 70, Task 3 and Task 4 durable process liveness): Recovery and teardown use `Get-Process` with a recorded PID, while state records no process start stamp. The live wrapper explicitly treats PID alone as unsafe because Windows recycles PIDs and compares pid plus pid_start instead. A resumed run can wait four hours on, or refuse teardown because of, an unrelated process. Planning should add and verify a start-time identity.
