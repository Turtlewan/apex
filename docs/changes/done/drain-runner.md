# Spec: Unattended queue drain runner
<!-- Governing contract: ~/.claude/skills/apex-code/references/spec-contract.md. -->

**Identity:** Run the read-only drain plan as a durable, serial, unattended set of Engine builds on local drain branches.
<!-- → why: see docs/technical/adr/ADR-049-unattended-queue-drain.md. -->

## Intent
- **Intent:** One on-demand command prints WILL BUILD and NEEDS YOU, launches a detached worker, and returns a drain id, report path, and resume command; a later attended session closes out the preserved Engine runs.
- **Invariants:** One drain per StateRoot and one drain per build repository; one Engine run at a time within a drain. Each committed spec follows a green full fence on the identical tree; failures restore manifest paths and skip dependents. The drain never mutates a ref that existed in a build repo before the drain started; its own `codex/drain-<id>` branch must not pre-exist. Each build repo's main worktree HEAD, index, and tracked file bytes stay unchanged. When the project is also a build repo, exempt only its drain report, named `<drain-id>.md` under the project's drain-report directory, from the main-worktree byte check. Hooks inherited by Engine-run Git commands are outside the drain's control (known limitation); boundary test fixtures install no hooks.
- **Invariants:** The drain never pushes, fetches, merges, rebases, resets, switches models, runs HOST checks, edits a spec, calls Engine `-Teardown`, or force-deletes worktrees or branches. Engine-created integration/task branches and worktrees (`codex/<spec>-<run8>-*` under the Engine default WorktreeRoot) are Engine-owned and permitted; nested temporary fixtures created by verify-fence suites are outside the drain's ref boundary. The only main-worktree write is the project drain report; the drain's only mutating operation aimed at a build repo's main worktree is `git worktree add`, apart from that report when the project is the build repo.
- **Non-goals:** Scheduled execution, notifications, queue re-sorting, attended review, close-out, and teardown.

## Assumptions
- `engine-linked-worktree` is built: the Engine accepts a linked `-Repo` worktree and hand-off writes to that target (`apex-engine.ps1:1743,1797`; `engine-git.ps1:498-512,587-607`). -> impact: Stop
- `engine-accept-timeout` is built: `-AcceptTimeoutMin` accepts 1–240 and defaults to 60 (`apex-engine.ps1:2-22`); this runner supplies 240 on new runs. -> impact: Stop
- The sorter emits schema version 1 with ordered `will_build` and `needs_you` entries (`apex-drain-plan.ps1:195-215`), and the build repo has a full fence readable by the baseline runner (`apex-baseline-check.ps1:27-39,228-280`). -> impact: Stop

Simplicity check: keep the sorter snapshot and use the Engine for each build; the runner owns only orchestration, recovery, final verification, commit, and reporting.
